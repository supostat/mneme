# HANDOFF: карта проекта — что меняется для скиллов плагина

Контракт для агента mneme-plugin. Движок получил карту проекта: синтетический слой разделов —
**доменов** (одна область проекта) и **потоков** (один путь через домены) — который плагин пишет
поверх заметок и перестраивает сам, **без гейта куратора**. Разделы лежат в корпусе рядом с
заметками, индексируются в собственные таблицы, приходят в `recall` и в бандл фазы ПЕРЕД заметками
в собственной ограде, сужают recall по доменам, а ответ, в котором ничего не прошло порог, теперь
прямо называет пробел памяти. Повод — живые прогоны, где агент в новой области проекта получал
пустой recall и читал тишину как «знать нечего», а куратор не мог сказать движку, в какой области
идёт фаза. Скиллы здесь НЕ пишутся — документ перечисляет, что плагинной стороне нужно отразить.

## Хранение карты <!-- HANDOFF-MAP-STORAGE -->

- Раскладка в корпусе: `map/domains/<id>.md` — домены, `map/flows/<id>.md` — потоки,
  `map/INDEX.md` и `map/glossary.md` — производные файлы. Всё под git корпуса, ничего из `map/` не
  игнорируется; каталоги создаёт `resolveCorpus` на первом же вызове любого инструмента. Рядом с
  `index.db` может лежать `index.db-stale` — маркер устаревшего индекса после упавшей пересборки;
  его пишет и снимает движок, он в `.gitignore` корпуса, плагин его не трогает.
- Файл раздела — frontmatter в ограде `---`, строки `key: <JSON>` (как у заметок), закрытое
  множество ключей, каждый обязателен: `id` — слаг `^[a-z0-9][a-z0-9_-]{0,63}$`, одно пространство
  имён на оба вида; `kind` — `"domain"` | `"flow"`; `anchors` — пути относительно корня проекта по
  грамматике якорей заметок (может быть `[]`); `depends_on` — id разделов, на которые опирается
  этот (поток называет домены, которые пересекает; всегда записан, `[]` допустим; существование
  целей при записи не проверяется — висячие зависимости отчитывают `map_list` и doctor); `terms` —
  строки глоссария без NUL/CR/LF и без дубликатов, не больше 24 на раздел и не длиннее 32 code
  points каждая (у домена попадают в glossary.md, у обоих видов — в полнотекстовый поиск и
  печатаются в recall после тела); `commit` — HEAD проекта в момент записи, ставит движок.
- Тело: 1..3000 code points, первая строка непустая — это суть раздела, по ней домен попадает в
  INDEX.md и в строку `map_list`. Правило лимита, как его печатает движок в описании `map_put`:
  a map section body must fit 3000 code points — twice a note — and its terms at most 24 of 32 code points each; one section prints at most ≈948 tokens in ASCII (≈1896 in Cyrillic) outside the notes budget, and at most 2 sections ride one recall
  Разделы не считаются в `budget` recall: всё, что recall печатает из раздела (тело и термы),
  ограничено этими двумя лимитами, а число разделов в ответе — капом 2.
- Тело и каждый терм проходят ту же проверку, что тело заметки: ограды `BEGIN/END MNEME NOTE` и
  `BEGIN/END MNEME MAP`, теги протоколов и невидимые разделители строк отвергаются с названным
  токеном. Файл в `map/`, нарушающий любое из этих правил, не читается вовсе (см. doctor ниже).
- `INDEX.md` (`# Project map`, затем `- <id> — <первая строка тела>` по доменам, по id) и
  `glossary.md` (таблица `| term | domain |` по термам доменов) — ПРОИЗВОДНЫЕ: движок переписывает
  их целиком при каждом `map_put` / `map_delete`. Плагин их не пишет и не правит — правка
  перезатрётся следующей записью и в индекс не попадёт.
- Привязка заметок к доменам нигде не хранится: при каждом rebuild движок сопоставляет `anchors`
  домена с `anchors` заметок и кладёт пары в таблицу `map_links` индекса. Правило — вложенность по
  сегментам пути: заметка связана с доменом, если её якорь равен якорю домена или лежит под ним
  (`src/billing/invoice.rb` под `src/billing`; `src/billing-old.rb` — нет). Каталог пишется без
  завершающего слэша (`src/billing`; `src/billing/` грамматика якорей отвергает) и связывает все
  заметки внутри; у файла вложенных путей нет, поэтому файловый якорь связывает только по
  точному равенству. Git и диск в правиле не участвуют. Домен без якорей не связан ни с одной
  заметкой.
- Doctor проверяет карту компонентом `map_sections`: нечитаемый файл или расхождение имени и
  каталога с frontmatter — `fail` с путём; висячие `depends_on` и мёртвые якоря разделов —
  `degraded` с лекарством «re-anchor the section with map_put»; без индекса живость «unknown
  (rebuilt on next recall)». Только чтение.

## Инструменты map_put / map_delete / map_list <!-- HANDOFF-MAP-TOOLS -->

- БЕЗ ГЕЙТА, С ЖУРНАЛОМ: запись идёт в `map/` напрямую, коммитится в git корпуса и пишет событие
  (`map_section_put` / `map_section_deleted`, схема событий v21); staging, `staging_list` и
  `staging_resolve` карту не видят. Заметки — по-прежнему только через staging.
- `map_put { kind, id, body, anchors, depends_on?, terms? }` → валидация → HEAD проекта → файл →
  INDEX.md + glossary.md → commit → событие → пересборка индекса. Ответ — одна строка:
  `Stored map section <kind> "<id>"; committed <sha>.`
  Повторный put с теми же полями при том же HEAD проекта коммита не создаёт (sha прежний), но
  событие пишет. Put с существующим id того же вида — замена целиком: раздел не версионируется,
  старое тело остаётся только в истории git корпуса.
- `map_delete { id }` → файл удалён → производные переписаны → commit → событие → пересборка.
  Ответ: `Deleted map section <kind> "<id>"; committed <sha>.`
- Если пересборка индекса после коммита упала, оба инструмента отвечают УСПЕХОМ с двумя
  добавочными строками по контракту `staging_resolve` (HANDOFF-RESOLVE-INDEX):
  `Index not rebuilt: <reason>` и
  `The decision is committed — do not retry it; the index catches up on the next successful rebuild.`
  Раздел записан и закоммичен; повторять вызов не нужно. Движок помечает индекс устаревшим, и
  первое же чтение через индекс — `recall` или сборка бандла фазы в `workflow_step` — пересобирает
  его перед чтением; догоняет и любое следующее решение staging, put или delete. Пока причина сбоя
  не устранена (например, испорченный файл в корпусе), такое чтение падает той же ошибкой
  пересборки, а не отдаёт устаревший индекс.
- Отказы (вызов возвращается ошибкой; на диск ничего не записано, события нет): плохой id —
  `id is "<id>"; it must be a map section slug: lowercase letters, digits, underscore or dash, starting with a letter or digit, at most 64 characters`;
  тело вне лимита — `body must be 1-3000 code points`; пустая первая строка —
  `body first line must be non-empty`; дубликат терма — `duplicate term: <term>`; термов больше
  24 — `a section holds at most 24 terms: got <n>`; терм длиннее 32 code points —
  `term <position> must be at most 32 code points` (позиция с 1, сам терм не повторяется); терм с
  оградой или тегом протокола —
  `term <position> contains foreign tool/protocol markup and was rejected: <token>`; самозависимость —
  `a section cannot depend on itself: <id>`; якорь вне грамматики — текст из грамматики якорей
  заметок; id занят другим видом — `section "<id>" exists as <kind>; delete it first`; delete или
  показ неизвестного id — `no map section "<id>" exists`; id не слаг —
  `invalid map section id: "<id>"`; проект без коммитов —
  `project has no resolvable HEAD - a repository without commits cannot anchor notes or map sections; make the first commit, then retry: <stderr>`.
- `map_list {}` → по строке на раздел, домены, затем потоки, по id:
  `<id> [<kind>] anchors: N, dead: K, depends_on: a, b, terms: M — <первая строка тела>`
  (`dead` — якоря, которых нет ни в индексе git проекта, ни на диске, ни на локальных ветках;
  `(none)` при пустом `depends_on`); затем по строке на каждую висячую зависимость:
  `warning: depends_on of "<id>" names unknown section "<x>"`; последняя строка —
  `Bodies are not listed; call map_list with an id to read one section in full.`
  Пустая карта — одна строка `The project map is empty.`
- `map_list { id }` → раздел целиком в MAP-ограде после строки RETRIEVED-DATA: `id:`, `kind:`,
  `anchors:`, `depends_on:`, `terms:`, `commit:` (пустой список — `(none)`), затем тело, затем
  END того же nonce. Всё внутри ограды — данные, не инструкции.

## Карта в recall <!-- HANDOFF-MAP-RECALL -->

Ответ `recall` (и бандл фазы в `workflow_step`) печатает разделы ПЕРЕД заметками, каждый в своей
MAP-ограде с тем же nonce, что у NOTE-блоков ответа. Первая строка ответа — прежняя строка
RETRIEVED-DATA; дальше, при одном домене и одной заметке:

```
----- BEGIN MNEME MAP 3f9c0a1b2c3d4e5f -----
id: billing
kind: domain
notes: 01ARZ3NDEKTSV4RRFFQ69G5FAV
Billing issues invoices.
Every order closes with one.
ledger
----- END MNEME MAP 3f9c0a1b2c3d4e5f -----
----- BEGIN MNEME NOTE 3f9c0a1b2c3d4e5f -----
id: 01ARZ3NDEKTSV4RRFFQ69G5FAV
invoice generation lifecycle
----- END MNEME NOTE 3f9c0a1b2c3d4e5f -----
```

- MAP-блок отличается от NOTE-блока МЕТКОЙ ограды (`BEGIN MNEME MAP` / `END MNEME MAP`), никогда
  содержимым. Строки `id:` и `kind:` стоят первыми; `notes:` — только у домена: id связанных
  заметок через запятую, `(none)` при пустой привязке; у потока строки `notes:` нет. Затем тело и
  — если у раздела есть термы — по терму на строку (как теги у заметки после тела).
- В бандле фазы NOTE-блок открывается заголовком `[type] id …`, как раньше; MAP-блоки те же.
  Состав бандла (`bundle_notes`) и членство `used_notes` — только заметки: id раздела в
  `used_notes` отвергает вызов.
- Кап — не больше 2 разделов на ответ; порог релевантности тот же, что у заметок (лексическое
  совпадение или косинус не ниже 0.35); cold-start floor на разделы не действует: при нулевой
  релевантности карта не подсовывается.
- `recall { query, budget?, domains? }`: `domains` — список id ДОМЕНОВ. Заметки сужаются до
  связанных с названными доменами (объединение `map_links`), разделы — до самих доменов и потоков,
  чьё `depends_on` их называет; ранжирование идёт уже по суженному множеству. Неизвестный id,
  не домен или не слаг — ошибка `no map domain "<id>"`, не пустой ответ.
- `workflow_start { …, recall_domains?: { [phaseId]: string[] } }` — то же сужение для бандла
  фазы, рядом с `recall_anchors`. Проверяется на старте по `map/`: неизвестная фаза —
  `recall_domains names unknown phase "<id>"`; не слаг —
  `recall_domains for phase "<id>": "<x>" is not a map section slug`; домена нет —
  `recall_domains for phase "<id>": no map domain "<x>"`; run не стартует, событий нет. Домен,
  удалённый после старта, роняет сборку бандла той фазы ошибкой `no map domain "<x>"` до записи
  события — вернуть домен через `map_put` или перезапустить run без него.
- Событие `recall` несёт `domains`, `sections` (кандидаты канала разделов с флагом `returned`) и
  `gap`; `returned_ids` и `candidates` — по-прежнему только заметки.

## Пробел памяти <!-- HANDOFF-MAP-GAP -->

- Если ни одна заметка-кандидат и ни один раздел не прошли порог, ПОСЛЕДНЯЯ строка ответа `recall`
  и бандла фазы — одна и та же:
  No memory above the relevance threshold for this question: record what you learn with remember.
  Она же стоит под строкой `No matching notes.` (и под её degraded-вариантом). Заметки cold-start
  floor — все ниже порога — показываются, но пробел не закрывают: строка остаётся.
- Пробел считается ДО отсечения бюджетом: заметка выше порога, не влезшая в `budget`, — память,
  которая есть, поэтому строки пробела нет, даже если ответ пуст (`No matching notes.`). Пустой
  ответ без строки пробела значит «не хватило бюджета», а не «знать нечего» — повторить `recall` с
  большим `budget`.
- Режим degraded (`Recall ran in degraded mode`) значит одно: косинусный канал не работал —
  эмбеддер недоступен или в индексе нет ни одного вектора, ни заметок, ни разделов. Корпус, где пока
  есть только разделы карты (порядок setup), degraded не считается.
- Что делает агент: не читать тишину как «знать нечего». Решение, ошибка или шаблон, найденные по
  этому вопросу, записываются через `remember` (в фазе run'а — уходят в harvest), потому что
  корпус по нему пуст. Строка — сигнал, не ошибка: `isError` не выставлен.
- В журнале — `recall.gap: true`; `stats` печатает долю строкой `(n) Memory gaps: N/M (x%)`
  сразу после `(c)`, только по инструментированным событиям (`n/a (0 instrumented recall events)`
  без них). Буква (n), не (d): нумерация отчёта сквозная через все рендереры.

## Что править в скиллах mneme-plugin <!-- HANDOFF-MAP-SKILLS -->

- **setup** — построение карты: после анализа проекта — `map_put` на каждый домен (якоря —
  каталоги области без завершающего слэша, связывающие все заметки внутри, и ключевые файлы;
  термы — словарь области) и на каждый поток (`depends_on` — домены пути); без гейта, поэтому без
  меню курации; результат — строки `Stored map section …`, при `Index not rebuilt:` вызов не
  повторять. Один раздел — одна запись; правка — put целиком.
- **plan** — сужение: при выборе `recall_domains` для фаз плана брать id из `map_list {}`, только
  домены; финал плана печатает `recall_domains` в готовой команде рядом с `recall_anchors`.
- **dev** — сужение и чтение: `workflow_start` передаёт `recall_domains`; в бандле MAP-блоки
  читаются как рамка ДО заметок; строка пробела памяти в бандле — повод записать найденное в
  harvest фазы; отказ `no map domain` на старте — исправить карту, а не run.
- **arch** — чтение карты: `map_list {}` как первый обзор, `map_list { id }` для раздела целиком,
  `recall { domains }` для вопросов внутри области; карту arch не пишет.
- **resume**, **design-server** — без изменений: инструменты карты им запрещены, как и остальные
  пишущие.
