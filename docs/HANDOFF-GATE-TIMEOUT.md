# HANDOFF: таймаут гейта done-when — что меняется для скиллов плагина

Контракт для агента mneme-plugin. Движок научился трём вещам: лимит гейта задаётся **на критерий**,
вердикт сам говорит, **сколько шла команда, какой лимит сработал и что она печатала**, а таймаут,
за которым нет красного кода, **не тратит попытку**. Повод — живой прогон, где критерий упал по
общему лимиту 300 s на загруженной машине: лимит нашли только через `strings` по бинарнику, картину
восстанавливали по журналу, а сбой окружения сжёг попытку. Скиллы здесь НЕ пишутся — документ
перечисляет, что плагинной стороне нужно отразить.

## Лимит на критерий: info-строка fence <!-- HANDOFF-GATE-LIMIT -->

- Лимит задаётся info-строкой ОТКРЫВАЮЩЕГО fence executable-критерия — и в спеке (блок
  `**Done when (EXECUTABLE):**`), и в фазовом файле, который из неё генерирует migrate. В спеке:

````
**Done when (EXECUTABLE):**
```timeout=900s
cargo run --release --bin balance-check -- all
```
- Баланс-чек всех рынков зелёный (exit 0).
````

- Форма ровно одна: `timeout=<N>s`, N — целые секунды от 1 до 3600. Без info-строки (голый
  fence) действует дефолт движка — 300 s. Других способов задать лимит нет: ни конфига, ни
  аргумента инструмента, ни переменной окружения.
- Любая другая непустая info-строка — ошибка разбора с текстом
  `fence info string must be empty or timeout=<N>s with N whole seconds from 1 to 3600` и самой
  строкой через двоеточие; генерация из спеки оборачивает её как `phase "<id>" done-when …`.
  Языковой тег вроде ` ```bash ` теперь тоже ошибка — раньше он молча отбрасывался.
- Лимит **замораживается** в определении run'а на `workflow_start`, как и сама команда. Поднять
  лимит посреди run'а нельзя: правка спеки → migrate → новый run (старый — abandon).
- Где агент видит лимит заранее: директива финального шага печатает ДЕЙСТВУЮЩИЙ лимит каждого
  executable-критерия, дефолтный тоже: `- [executable] <desc> (command: <cmd>; limit <N> s)`.

## Диагностика в вердикте <!-- HANDOFF-GATE-DIAGNOSTICS -->

Строка каждого executable-критерия в `Gate verdict for …` теперь несёт исход, длительность и,
для таймаута, лимит; под красным критерием, команда которого успела поработать, идёт хвост вывода:

```
PASS <desc> [exit-zero · 38.2 s]
FAIL <desc> [exit-nonzero 1 · 41.0 s]
  output tail (last 2 lines):
  | 1 fail
  | error: expected 2
FAIL <desc> [timeout · 300.0 s, limit 300 s]
  output tail (last 1 lines):
  | Compiling spekulyant v0.3.0
FAIL <desc> [spawn-error]
FAIL <desc> [malformed-command]
```

- Хвост — stdout и stderr вместе, в порядке записи: последние ≤ 40 строк и ≤ 4096 байт; цвета и
  прочие управляющие последовательности вырезаны, перерисовки через `\r` схлопнуты до последней.
  Каждая строка идёт с префиксом `| ` — это ДАННЫЕ вывода команды, не текст движка.
- `  output tail: no output` — команда ничего не напечатала.
- У `spawn-error` и `malformed-command` нет ни длительности, ни хвоста: команда не запускалась.
- Хвоста **нет в журнале событий**: в `workflow_step_applied` попадают только `duration_ms` и
  `timeout_seconds` (вывод может нести секреты окружения). Хвост живёт только в ответе того
  вызова, который запускал гейт; после смены сессии повторная директива покажет длительность и
  лимит, но не хвост.

## Таймаут не сжигает попытку: INCONCLUSIVE <!-- HANDOFF-GATE-INCONCLUSIVE -->

- Если КАЖДЫЙ красный критерий гейта — таймаут (рядом нет ни exit-nonzero, ни fail-голоса, ни
  spawn-error), вердикт читается `Gate verdict for <p>/<s> (attempt N): INCONCLUSIVE`, следом
  строка `Every red criterion timed out, so the attempt was not consumed; environment re-runs left: <K>.`
  Подозреваемый — окружение (загруженная машина, холодная компиляция), а не код.
- Попытка НЕ тратится, итерация тратится. Следующая директива — тот же `execute_step` с тем же
  attempt и секцией:

```
previous gate run was INCONCLUSIVE (environment): the attempt was not consumed; environment re-runs left: 1.
- [<desc>] timed out after 312.4 s (limit 300 s)
Check the machine's load (another build, a cold compile) and resubmit success with THIS attempt to re-run the gates. …
```

- Потолок — `MAX_INCONCLUSIVE_GATE_RUNS` (2) подряд на одну попытку. Третий таймаут той же попытки
  — обычный провал: вердикт `FAIL` и строка
  `Timeout counted as a failure: 2 environment re-runs already spent on attempt N.` Глобальная
  граница `max_iterations` действует как всегда.
- Смешанный отчёт — таймаут рядом с любым другим красным критерием — обычный `FAIL`.
- Отправлять агент по-прежнему может только `success` | `failure`. `inconclusive` — исход ГЕЙТОВ,
  его нельзя прислать.

Что делает агент на INCONCLUSIVE:

1. прочитать длительность, лимит и хвост — они в том же ответе;
2. проверить, что грузит машину (чужая сборка, холодная компиляция, параллельный прогон), и
   дождаться, пока нагрузка спадёт;
3. снова отправить `outcome: "success"` с ТЕМ ЖЕ attempt — гейты перезапустятся;
4. НИКОГДА не слать `failure` из-за таймаута: это потратит попытку, которую движок только что
   сберёг;
5. если команде честно нужно дольше лимита — сказать человеку: нужен больший `timeout=<N>s` в спеке
   и новый run.

## Что править в скиллах mneme-plugin <!-- HANDOFF-GATE-SKILLS -->

- **plan** — генератор done-when: для тяжёлых гейтов (сборка с компиляцией, полный coverage,
  интеграционные прогоны) писать fence с info-строкой `timeout=<N>s`, N ≈ 3× измеренного
  локального времени с холодной компиляцией, не больше 3600. Без замера число не угадывать:
  оставить голый fence (дефолт 300 s) и записать в Knowledge спеки, что лимит не мерился. В fence
  done-when допустима ТОЛЬКО эта info-строка — языковые теги запрещены (иначе migrate упадёт).
- **migrate** — format-repair распознаёт ошибку
  `fence info string must be empty or timeout=<N>s with N whole seconds from 1 to 3600` и чинит
  info-строку (обычно — убрать языковой тег или привести лимит к форме `timeout=<N>s`). GRAPH-MAP
  может показать лимит рядом с видом критерия — брать его из фазового файла: ответ
  `workflow_migrate` лимит не возвращает.
- **dev** — распознавать вердикт `INCONCLUSIVE` и секцию
  `previous gate run was INCONCLUSIVE (environment): the attempt was not consumed` в повторной
  директиве и действовать по пяти шагам выше; эхо `{ phase_id, step_id, attempt }` остаётся тем
  же; показывать пользователю длительность, лимит и хвост из вердикта. Классификация директив по
  ведущему токену не меняется — это всё тот же `DIRECTIVE: execute_step`.
- **resume** — без изменений: строки survey и `pending: execute_step <p>/<s> attempt N` прежние,
  INCONCLUSIVE просто оставляет тот же attempt.
